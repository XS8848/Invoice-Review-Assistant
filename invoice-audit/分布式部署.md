# 发票审计系统 · 分布式部署指南

> 本文说明如何把单机部署的服务拆分到多台机器/多个节点，以及分布式部署的核心要点。

---

## 一、服务分块（组件拆分）

系统已按组件拆分，通信全部走 **FastAPI（HTTP/JSON）**，组件地址通过环境变量配置：

```
                    ┌─────────────────────────────────────────────┐
                    │  ① API 主服务 (app.main, 端口 8000)          │
                    │     认证/上传/查询/审查/调参/监控/看板         │
                    │     状态机调度器 dispatcher（轮询+原子领取）  │
                    └───────────┬──────────────────┬──────────────┘
              OCR_SERVICE_URL  │                  │  LLM_SERVICE_URL
                    ┌──────────▼──────────┐  ┌────▼─────────────────┐
                    │ ② OCR 组件服务      │  │ ③ LLM 组件服务        │
                    │  ocr_server (8101)  │  │  llm_server (8102)    │
                    │  GPU 推理/清洗      │  │  DeepSeek 工具调用     │
                    └──────────┬──────────┘  └──────────────────────┘
                               │ 读文件
                    ┌──────────▼──────────┐   ┌──────────────────────┐
                    │ ④ MinIO（9000）     │   │ ⑤ MySQL（3306）      │
                    │  发票对象存储        │   │ 共享库（claims/配置） │
                    └─────────────────────┘   └──────────────────────┘
```

| 组件 | 启动 | 端口(env) | 依赖 |
|---|---|---|---|
| ① API+调度 | `bash backend/run_backend.sh` | APP_PORT=8000 | MySQL、MinIO、OCR/LLM 地址 |
| ② OCR | `bash backend/run_ocr_server.sh` | OCR_SERVER_PORT=8101 | MySQL(读调参)、MinIO(取文件)、GPU |
| ③ LLM | `bash backend/run_llm_server.sh` | LLM_SERVER_PORT=8102 | MySQL(读调参)、DeepSeek Key |
| ④ MinIO | `bash start_minio.sh` | 9000/9001 | — |
| ⑤ MySQL | `infra/install_mysql.sh` | 3306 | — |

## 二、切换模式（两个环境变量）

| 模式 | 配置 | 说明 |
|---|---|---|
| **内嵌**（单机默认） | `OCR_SERVICE_URL=` `LLM_SERVICE_URL=`（留空） | 组件在 API 进程线程池内执行 |
| **远程**（分布式） | `OCR_SERVICE_URL=http://gpu节点:8101` `LLM_SERVICE_URL=http://llm节点:8102` | 调度器经 HTTP 调用组件服务 |

配置位置二选一（可同时）：
- `invoice-audit/.env`（应用级，后端直接读取）
- `deploy.env`（部署级，deploy.sh 会以环境变量导出，**优先级高于 .env**）

> 组件服务自身也读 `.env`：分布式模式下每个节点只需一份 .env 副本，改 `DATABASE_URL/MINIO_ENDPOINT` 指向共享的 MySQL/MinIO，并按需设置 `OCR_SERVER_PORT/LLM_SERVER_PORT`。

## 三、逐步迁移路径（单机 → 分布式）

1. **现状**：全部内嵌，单机 localhost
2. **拆 LLM**：在任一节点起 `llm_server` → API 的 `LLM_SERVICE_URL` 指向它 → 重启 API
3. **拆 OCR**：在 GPU 节点起 `ocr_server`（需装 paddle GPU 环境）→ `OCR_SERVICE_URL` 指向它 → 重启 API
4. **拆存储/库**：把 MinIO/MySQL 迁移到独立节点，各节点 `.env` 改 `MINIO_ENDPOINT`/`DATABASE_URL`
5. **API 多副本**：多台跑 `run_backend.sh`，前置 Nginx 负载均衡 + JWT_SECRET 保持一致

## 四、分布式部署要点（关键注意事项）

1. **共享数据库是协调核心**：所有 API 副本连同一 MySQL。状态机的原子领取（`UPDATE ... WHERE queue_state=1`）在共享库上天然支持多调度器实例并发，不会重复处理；租约回收同理。
2. **JWT_SECRET 必须全副本一致**：不一致会导致登录态互相校验失败。
3. **系统提示词/报销规则/视觉参数在共享 configs 表**：任何节点改调参，其他组件下次任务自动读到最新值（组件服务启动时从 DB 加载，任务执行时内存热读）。
4. **MinIO 预签名 URL 与访问来源匹配**：后端已实现 Host 自适应（请求经哪个地址进来，预签名就用哪个地址的 :9000）。分布式下若组件与 API 分属不同网段，请确认客户端浏览器能直达 MinIO 端口（或用域名统一）。
5. **OCR 组件要自己能从 MinIO 取文件**：调度器只传 `file_key`，OCR 服务按自己的 `MINIO_ENDPOINT` 下载——务必配置正确。
6. **OCR 是 GPU 瓶颈**：单 OCR 服务约 21 张/分钟；多 GPU 节点可起多个 ocr_server，但当前调度器是单地址直连——多副本扩展建议：Nginx/LVS 轮询 OCR 服务地址，或按 GPU 分组路由（留作扩展点）。
7. **LLM 服务无状态**：可任意多副本；DeepSeek 并发限制 2500，`LLM_WORKERS` 按需调。
8. **时钟同步（NTP）**：锁租约/时间戳依赖时间；多机部署务必 NTP 对齐，避免租约误回收。
9. **健康检查与监控**：所有组件都有 `GET /health`；API 的 `/api/monitor` 只反映本机资源——分布式下建议配合 prometheus-fastapi-instrumentator（已内置）统一采集。
10. **降级行为**：远程 LLM 服务不可用时，单据自动转人工（不丢单）；远程 OCR 不可用时单据进入"系统异常"（看板可重派）。建议加告警盯组件 /health。
11. **安全**：组件间通信无内建认证（FastAPI 直连）——务必放在**可信内网**，或用网关加 Token；生产建议组件端口不暴露公网。
12. **网络与防火墙**：8000/8101/8102/9000/3306 端口在对应节点放行；跨机部署用 `deploy.env` 填内网 IP（不再写死任何绝对路径，全部环境变量化）。
